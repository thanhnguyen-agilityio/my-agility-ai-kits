WHY A REPEATABLE FLOW

Three constraints, one answer

Slow answers

Answers to open questions can take days. You cannot wait for every one.

Locked-down machine

Work runs on a virtual machine with limited permissions. The AI may not be able to build or run tests.

Strict house rules

A codebase with rule files, analyzers and a reviewed contract.

60 API routes

delivered in about 10 weeks, all through the same seven steps.

The top track is the real stage on our project. Two of the four gates came from the setup, not from the workflow. All work ran on an Azure Virtual Desktop with limited permissions, and the dev environment had to run in a slow dev container that Claude could not run in. So we used two VS Code windows: window one in the dev container to build, run unit tests and call the API through .http files; window two where Claude wrote code but could not build or run it. A person carried test results back and forth. Client answers took two to three days, and a person settled conflicts. Settle stays even in good conditions, because planning raises new questions that loop back to the grill. The client owned the PRs, so a person approved any change a caller would notice. In good conditions, with fast feedback or authority to decide, a machine Claude can build on, and ownership of the PR, the same seven steps need only two human steps: answering the grill questions and settling the decisions planning raises.

STEP 1 · GRILL · writes questions.md

Ask every open question before planning

Rounds, not a dump. Each round asks only what can be answered now.

A recommended answer on every question, worded so “yes” accepts it.

Facts are the AI’s job. It looks them up; you only make decisions.

EXAMPLE QUESTION

“Classifications” could mean managing the label list, or applying a label to a file. Which one?

Recommended: applying a label, plus a read-only list of labels.

You decide: which answers to accept, and which questions go to the client.

Agility · AI kit

5

The grilling skill is from Matt Pocock’s public skills repo. Its trick is the recommended answer: the client can reply “yes, yes, no” instead of writing paragraphs. Slices whose questions were answered early needed far fewer rewrites.

STEPS 2–3 · SYNC ISSUE, PLAN · writes requirements.md, plan.md

Sort every requirement into three buckets

Decided

Confirmed in the thread. Goes into Phase 1 and gets built now.

Waiting

An open question. Goes to Phase 2, with the question ready to post.

Conflict

Two sources disagree. Both are cited. The AI never picks one.

The plan reads the ticket, the client’s comments, the project rule files and the vendor docs. Every claim cites a source or says “assumption”.

You decide: settle each conflict and agree what Phase 1 covers.

Agility · AI kit

6

Sync issue copies the ticket and the client’s comments into local files and drops noise like screenshots. The plan step then does the sorting. The two phases are what let us keep building while the client took days to answer: Phase 1 is only decided work.

STEP 4 · IMPLEMENT · writes code + tests

Code in the house style, with tests

Reads the whole plan first

Stops and asks when the plan is unclear or clashes with the code.

Copies the surrounding style

No dead code, no speculative layers, comments only for “why”.

Aims tests at 95% of branches

And names the paths it is not sure are covered.

Flags calls it won’t make

Architecture, ownership and judgment calls come back to you.

On our project: a person built, ran the unit tests and called the API via .http, in a second VS Code window (slide 4).

Agility · AI kit

7

This step is a command, not a skill: /implement-plan with the plan file. On our project Claude could not run inside the dev container on the VDI, so one VS Code window ran the build and tests and another held Claude; a person moved results between them. If your environment can build, let the AI run them too, but keep the rule that it never claims green without a real run.

STEPS 5–6 · REVIEW, FIX REVIEW · writes review.md, reply.md

Review against the rules, not memory

Review

Re-reads the project’s rule files every run. Read-only; writes one report.

Critical · a bug or a broken rule

Important · a gap with a workaround

Suggestion · style and wording

Every finding: file, line, what is wrong, the fix.

Fix review

For each finding: verify, explain, fix with a test, then one reply line.

Done: the registration test now covers all four helpers.

Not changed: the client already searches parent folders.

Still open: waits on the owner’s answer.

You decide: which findings are real, and approve any change a caller would notice.

Agility · AI kit

8

The review skill is strict on purpose: it does not review from memory. Most findings are a line that disagrees with one of the project’s own rule files. The fix-review skill works on any review file, including a teammate’s, and drafts the reply so every finding ends with a reason.

Agility · AI kit

9

The PR skill reads the diff and the code, not the commit messages, and a small script lists the commits, the stats and any new routes. The rule I like most: cut any sentence that would read the same on a different PR. It kills filler.

WHY YOU CAN TRUST THE OUTPUT

Five rules the skills never break

01

Cite or say “assumption”

No claim in a plan without a source.

02

Read the rules, not memory

Plan and review re-read the rule files every run.

03

Never pick a side

Conflicts go to a person to settle.

04

Stop on the wrong state

Wrong branch, uncommitted work or a missing input stops the skill.

05

Never claim green

No “tests pass” unless they ran in this session.

Agility · AI kit

10

Each rule is one line in a skill file. Together they are why we could read the AI’s plan or review and trust it enough to act. The most valuable one is never picking a side: when two sources disagree, the AI lists both and stops.

WHAT THE AI MISSED

The review checked rules, not resource use

167 hosts

A test helper built a full web host for every test. It passed every review, then ran CI out of memory.

no number

The implement step aims at 95% coverage but cannot measure it. Nobody recorded the real figure.

Fix 1: add test cost to the review checklist (hosts per test, memory, CI timeouts).

Fix 2: record the coverage number at every merge.

Agility · AI kit

11

Being honest about the limits makes the rest believable. The AI reviewer only checks what its checklist says. Our checklist had no line about test cost, so a helper that built 167 web hosts sailed through. A sibling helper already shared one host; nobody compared them.
